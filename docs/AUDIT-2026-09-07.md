## 1. Findings (verified)

IDs are per-surface (`I-` iOS, `B-` backend, `T-` Telegram bot, `W-` website, `C-` CI/infra), numbered in order of appearance, not severity.

### High

#### I-1 · App Attest key survives device migration, the Secure Enclave key does not — auth dies permanently until reinstall `[iOS, auth-token-lifecycle]`
`AttestationService.swift:119-126` catches only `AttestationError.reattestationRequired`; `refresh()` (:154) calls `service.generateAssertion(keyID, ...)` which throws `DCError.invalidKey` when the Secure Enclave key is gone. The key id lives in `UserDefaults` (:146, restored by iCloud/Quick Start); the bearer token is `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` (`TokenStore.swift:60`) so it does *not* migrate — forcing a mint on the new device that fails client-side before any server round trip. `TokenStore.swift:191-195` swallows the error and sends unauthenticated; every retry hits the same 401 → `.sessionExpired` → "reinstalling the app will reset it." No caller of `reset()` clears the stale key id; no test covers `DCError`/`invalidKey`.
**Impact:** any user who moves to a new iPhone via backup/Quick Start gets a dead app — every scan, listing and trends call fails forever.
**Fix:** in `mintToken`, also catch `DCError` (`.invalidKey` and other non-transient codes), clear `Keys.keyID`, fall through to `attestFresh()`. Effort S.

#### I-18 · In-app Privacy Policy still omits Google/TelemetryDeck/Telegram and says data isn't shared — the web policy was fixed, the shipped copy wasn't `[iOS, security-privacy]`
`LegalView.swift:7` is dated "September 2, 2026"; `:19` "We do not sell, rent, or share your photos or device identifier with third parties." No mention of TelemetryDeck, Google/Gemini or Telegram anywhere in the file. `backend/main.py:980` (Sept 3) has the corrected text — Service Providers: Google (Gemini), TelemetryDeck, Telegram. `git show e88f110` touched only `backend/main.py` and tests, not `LegalView.swift`. **AUDIT-2026-09 A-1 is marked "done in PR #83," but only the web copy changed — this is exactly the kind of stale-tracked item this pass was asked to flag.** Neither copy mentions the DeviceCheck token now sent on every fresh attest (`AttestationService.swift:143,166-169`) and persisted server-side (`auth.py:270-272`).
**Impact:** the paywall's own privacy link (`PaywallView.swift:132,187-189`) shows App Review and EU users a policy that denies sharing that actually happens. GDPR Art. 13 accuracy problem + 5.1.1 review risk.
**Fix:** copy the Sept 3 web text verbatim into `PrivacyPolicyView`, bump `updated`, add the DeviceCheck sentence to both, add a test asserting the in-app text contains "TelemetryDeck"/"Google"/"Telegram." Effort S.

#### I-23 · Server 402 (quota spent) is shown as a "Scan Failed" dead end instead of routing to the paywall `[iOS, dead-end-flow]`
`AppError.swift:92-98`'s own comment says of 402: "Both route to the paywall" — but `.quotaExceeded`/`.proRequired` appear nowhere outside `AppError.swift`. `ScanViewModel.swift:130-135` just sets `errorMessage`; `ScanView.swift:287-294` renders it under `.alert("Scan Failed", ...)` with only OK. Analytics buckets it as `scan_failed{reason:no_result}`. The concrete trigger is the local-day-vs-UTC-day skew (`Calendar.current.isDateInToday` at `ScanViewModel.swift:263` vs `_utc_day()` at `quota.py:79-80`) plus counter drift — **not** the DeviceCheck reinstall path, which the mint response's `free_scans_remaining` already catches client-side before this point.
**Impact:** the user hits a dead-end error alert at the exact moment of highest purchase intent; the misfiled `no_result` event corrupts the very funnel `FREE_SCANS_FIRST_DAY=3` is being read against, starting today.
**Fix:** in the two `startScan`/`scanItem` catch blocks, special-case `.quotaExceeded`/`.proRequired` → `showPaywall = true`, `freeScanLimitHit` tracked, instead of `errorMessage`. Effort S.

#### B-1 · `/scan` buffers the entire upload into memory before the 10 MB check `[backend, request-size-limits]`
`main.py:1088` checks `file.headers.get("content-length")` — a multipart *part* header nobody sends — and `main.py:1096` `image_bytes = await file.read()` runs before the `>10MB` check at `:1098`. Installed Starlette 1.6.0's `max_part_size` only guards non-file parts; file parts spool with no ceiling. `backend/Dockerfile:57` runs `uvicorn ... --workers 1`. `_enforce_limits` doesn't even run until after this read (main.py:1130).
**Impact:** any token holder can POST a multi-GB part and OOM-kill the single replica, taking every in-flight scan with it.
**Fix:** check the request-level `Content-Length` header before parsing; replace `file.read()` with a chunked read that 413s once 10MB+1 is seen. Effort S.

#### B-14 · Per-IP rate-limit key is client-controlled unless `TRUSTED_PROXY` is set `[backend, security]`
`Dockerfile:57` runs uvicorn with `--forwarded-allow-ips='*'`. Installed uvicorn 0.52.4 then trusts the **leftmost** (client-supplied) `X-Forwarded-For` hop as `scope['client']`. `main.py:496-502` only parses the header itself (rightmost hop) when `_TRUSTED_PROXY` is truthy; otherwise it uses that spoofable value. `docs/RUNBOOK.md:470` lists `TRUSTED_PROXY=true` as an **unticked** launch-checklist item and both the runbook and `AUDIT-v2.md:1062` mis-describe the failure as "collapses to one bucket" — it is the opposite: fully spoofable, one bucket *per request*.
**Impact:** if `TRUSTED_PROXY` is unset in Railway (not verifiable from the repo), the 60/h IP backstop — RUNBOOK's "the real backstop" — is fully bypassable. Every route behind it still sits behind App Attest, so the practical floor is per-subject quota, not the IP limiter.
**Fix:** stop depending on the env flag — always take the rightmost XFF entry when the header is present, truncate the key. Correct RUNBOOK.md:470 / AUDIT-v2.md:1062's description. Confirm the Railway variable today. Effort S.

#### C-1 · Secret scanning (gitleaks) only runs when `ios/**` changes — backend, website, docs commits are never scanned `[CI, secrets-exposure]`
`.github/workflows/ios.yml:3-13` gates the *whole* workflow, including the `secrets-check`/gitleaks job (:144-174), behind `paths: ios/**`. `backend.yml` has no gitleaks step at all — only a `git ls-files --error-unmatch .env` check. Verified against real runs: the last gitleaks scan was 2026-09-04 (run 33893610576); five backend-only pushes deployed 09-05..09-07 with zero scans. **`docs/AUDIT-2026-09.md:69` states "gitleaks on every push" — false, and the real secrets (Gemini key, Telegram token, App Store Server API key) live exactly in the backend files this misses.**
**Impact:** a credential pasted into `backend/*.py`/`notify.py` reaches main and production with no scanner ever run.
**Fix:** move `secrets-check` to its own workflow, no `paths:` filter; correct AUDIT-2026-09.md:69. Effort S.

#### C-2 · Deploy job cannot fail: `railway up --detach` returns before the build, and a missing token exits 0 `[CI, deploy-verification]`
`backend.yml:200-203` `exit 0` (with only a `::warning::`) when `RAILWAY_TOKEN` is unset. `:255` is the workflow's last line: `railway up --service snapworth-backend --detach` — nothing polls the result. Real deploy log (job 101710364951, 2026-09-07): the step lasted 2 s, ended at "Uploading..." with no build/boot confirmation. The workflow's own comments (~lines 233-245) document a *real prior incident* where a deploy silently didn't take effect.
**Impact:** "Deploy → Railway" is green whether or not the container built or booted; a boot-time refusal (`tokens.py:170-172`, `main.py:213-217`) looks identical to success. The only detector today is a human noticing the Telegram deploy ping never arrived.
**Fix:** `exit 1` on missing token; poll `/health` (or `/health/ready`) for up to ~3 min until `commit == $GITHUB_SHA`, fail the job otherwise. Effort S.

#### I-2 · Pending purchase (Ask to Buy / SCA) reported as complete — paywall dismisses with no subscription `[iOS, storekit-entitlement]`
`StoreKitPurchaseService.swift:70-73` `case .pending: break` returns normally; `PaywallViewModel.swift:39-40` sets `isPurchaseComplete = true` unconditionally on any non-throw; `PaywallView.swift:184-186` dismisses on that flag. `isSubscribed` stays false — the paywall reappears on the next scan with no explanation. Fix: distinguish `.pending` in the return type/error; only complete on `.success`. Effort S.

#### I-3 · Quota-backend blip at token mint writes a sticky 0 that locks the free user out for the rest of the local day `[iOS, offline-degradation]`
`TokenResponse.freeScansRemaining` is a non-optional `Int` (`AttestationService.swift:260`); on `QuotaUnavailable` the server sends `min(0, 10_000)` (`auth.py:196-204`) — deliberate fail-closed server-side (comment at :202). The client writes that 0 into the day-stamped `FreeScanCounter.serverRemaining` unconditionally (`:213-215`) and prefers it over the local `used` count (`ScanViewModel.swift:310`); the pre-flight gate never re-contacts the server to clear it. `/scan` itself sends `null` on the identical outage (`ScanAPIClient.swift:25-28`) — the mismatch is purely that `TokenResponse.freeScansRemaining` isn't `Int?` like the scan response is. Fix: make it `Int?`, only write non-nil. Effort S.

#### I-4 · Client resets the free allowance at local midnight, server counts UTC days; the 402 is misrouted (see I-23) `[iOS, state-consistency]`
`Calendar.current.isDateInToday` (`ScanViewModel.swift:263-264,289-291`) vs `_utc_day()` (`quota.py:79-80,115`). Reachable window is 00:00–03:00 local for UTC+1..+3 users (Romania is UTC+3 — the operator's own commit timestamps). The daily route to the same 402-misrouting bug is I-5, not this timezone skew. Fix: stamp with the server's `X-Quota-Resets-At` header instead of local midnight. Effort S.

#### I-5 · Thrift Flip scans never record the server's `free_scans_remaining` — Scan tab over-reports and lets a scan through to a 402 `[iOS, state-consistency]`
`ThriftFlipViewModel.swift:69` only calls `FreeScanCounter.increment()`; `ScanViewModel.swift:91-96` additionally writes `FreeScanCounter.serverRemaining`. Because `remaining` prefers the non-nil server value (`ScanViewModel.swift:310`), a Thrift Flip scan that consumes the last allowance leaves the Scan tab showing the pre-scan count — on the `FREE_SCANS_FIRST_DAY=3` welcome day: mint writes 3, three Thrift Flip scans later the tab still says "3 left," the 4th scan 402s. This is the **daily** trigger for I-23's misrouted alert. Fix: one line — `FreeScanCounter.serverRemaining = response.freeScansRemaining` after a Thrift Flip scan too. Effort S.

#### I-6 · Ledger follow-up for an item listed 14+ days ago is rescheduled with a past fire date on every foreground `[iOS, notification-scheduling]`
`syncEligible` (`NotificationManager.swift:338-341`, runs every foreground) calls `scheduleLedgerFollowUp` for every `.listed` item with no `fireDate > Date()` guard (contrast `syncTrialReminder` at :254, which has one); `add()` (:445-467) unconditionally schedules and tracks `.notificationScheduled`. Certain: unconditional re-add + inflated `notification_scheduled` metric per stale listing per foreground. Platform-behavior (whether iOS delivers the past-dated trigger immediately) not verifiable from source but is the commonly-observed behavior. Fix: guard `fireDate > Date()` in `add()`. Effort S.

#### I-7 · Paid/sold/fees fields parse with `Double(String)` — comma-decimal input from the locale keypad is silently discarded `[iOS, input-correctness]`
`ResultView.swift:191-199` writes `Double(newValue)` on every keystroke straight onto the `@Model` for all three money fields; `.decimalPad` (:303,402,647) emits the locale's separator. `Double("12,50")` is `nil` — the value vanishes with no error shown. `ThriftFlipViewModel.swift:159-163` already has the comma-tolerant parser. Fix: route all three through that parser, write only on successful parse. Effort S.

#### I-8 · `maxPhotoDimensions` hard-coded to 4032×3024 with no check against `supportedMaxPhotoDimensions` — crashes on 8MP iPads `[iOS, api-misuse]`
`CameraManager.swift:68-72` sets the value unconditionally. `TARGETED_DEVICE_FAMILY = 1` (iPhone-only target) still installs on iPad in compatibility mode; iPad 6-9/mini5/Air3 have 8MP (3264×2448) cameras. AVFoundation raises `NSInvalidArgumentException` (process abort) for an unsupported value — platform contract, not verifiable in-repo, but the population and mechanism are real. Shipped since 1.2.0 with no reports because every iPhone's 12MP+ camera supports 4032×3024. Fix: pick the largest `activeFormat.supportedMaxPhotoDimensions`. Effort S.

**Backend**

#### B-2 · Free-scan quota check and consume are two separate Redis ops; concurrent scans from one device all pass (docstring claims atomic) `[backend, quota-race]`
`quota.py:9-10` docstring: "the increment and the limit check are one operation." Reality: `check` (:147-155) only GETs; the INCR is in `consume` (:163), called from `main.py:1141` **after** `_analyse` returns. Reproduced this session: 5 concurrent check→sleep→consume tasks against `limit=1` → all 5 reached the model, counter ended at 5. Only `consume` is atomic; `check` is a plain read — bounded by the 20/h device and 60/h IP limiters, not unbounded. Fix: reserve atomically (`INCR` before the model call), refund on model failure. Effort M.

#### B-3 · During a Redis outage every Pro subscriber is silently read as free `[backend, cache-fail-open]`
`entitlements.py:582` `cache.get(...)` with no `required=`; `cache.py`'s fallback returns `None` on primary failure → `current()` returns FREE. `/listing` then 402s a paying subscriber; `/scan`'s quota path fails closed the *other* way (`required=True` → 503). Nothing distinguishes "Redis said free" from "Redis was unreachable." Needs a Redis outage to coincide with one of 2 comped subscribers scanning — real but rare today. Fix: distinguish unavailability from a genuine miss; fall back to the token's `tier` claim for its remaining lifetime. Effort M.

#### B-4 · Server timeout+retry (2×60s) exceeds the iOS client's 35s timeout; the retry can only bill Gemini and consume the user's free scan for a result nobody receives `[backend, timeouts]`
`aiconfig.py:180` `REQUEST_TIMEOUT_MS=60000`; `main.py:1344` `_RETRY_ATTEMPTS=2`, and a timeout is retryable. `CertificatePinning.swift:149,154` caps the client at 30s request / 35s resource. No `is_disconnected()` check anywhere in backend/ — `consume_quota` (main.py:1141) runs unconditionally after `_analyse`. Gemini Flash rarely exceeds 35s in practice, so this is a rare-incident cost, not a routine one. Fix: `GEMINI_TIMEOUT_MS≈25000` + check `request.is_disconnected()` before charging quota. Effort S.

#### B-5 · Unauthenticated `/auth/challenge`, `/auth/attest`, `/auth/refresh` have no rate limit `[backend, exceptions-on-request-path]`
`_enforce_limits` is called only at `main.py:1130/1609/1651` — never in `auth.py`. `challenge()` writes a Redis key with no principal and no limiter; `attest` runs a full x.509 chain walk unthrottled. Downgraded from the finder's high: keys are ~60 bytes with a 300s TTL, verification is milliseconds, and Railway's edge is an unknown extra layer — but it's a real, proportionate three-route hardening gap. Fix: apply the existing IP limiter to these three routes. Effort S.

#### B-16 · Subscription sharing is device-*counted*, not device-*bound* — docs still promise a bound that doesn't exist `[backend, security]`

**Telegram bot**

#### T-1 · One exception inside `poll_once` poisons the batch: offset never advances, bot silently stops answering `[bot, correctness/reliability]`
`notify.py:1413` `text.split(None, 1)[1]` raises `IndexError` on a message like `"/ask "` (trailing whitespace — real Telegram clients trim this, so the concrete repro is unlikely, but the structural gap is real). `poll_once` has no per-update try/except; `_command_loop` (:1440-1450) catches at the batch level, so `offset` never advances and the same batch re-polls every 5s until Telegram's ~24h update expiry or a manual offset bump. #### T-2 · "New Pro subscription" alert consumes its 400-day guard before sending, ignores send failure `[bot, reliability]`

Fix: hand the guard back on a failed send, mirroring `_announce_deploy`. Effort S.

#### T-3 · A failing photo test scan is counted as a failed user scan, can trigger the "Device paused" alert `[bot, correctness]`

At 1-4 real scans/day, one operator test photo the model can't price is a 25-100% distortion of the day's failure rate. Fix: pass a `count: bool` flag through `_analyse`, `False` from `_bot_scan`. ### `/scan` request path — Redis and model call counts

Per successful `/scan`, today's code makes roughly:

| Stage | Calls | Notes |
|---|---|---|

## 5. What the critic said is missing

> **Silent-failure bugs have no telemetry channel — the audit's own top findings would ship invisibly.** `ios/SnapWorth/Services/CrashReporter.swift` only forwards MetricKit crash/hang/CPU counters ("What is deliberately NOT forwarded" — no error events at all). None of the highest-severity findings above (App Attest key-mismatch lockout, 402 not routed to paywall, quota sticky-zero, `ThriftFlipViewModel` never recording `free_scans_remaining`) are crashes — they're silent logic failures. There is no non-fatal/logged-error analytics event anywhere I can find, and `TelemetryDeckAnalytics` is opt-outable, so once 1.3.5 ships these bugs are undetectable except via support email or churn. This is a whole class of bug (silent auth/quota/paywall-routing failures) the current instrumentation cannot surface, and it's not called out as a gap itself.
>
> **No App Store Server Notifications (webhook).** `grep -rn "app_store_notifications\|/inApps/v1\|ASN" backend/entitlements.py` returns nothing — entitlement state is refreshed only when the client calls in (`/auth/refresh`), not pushed on refund/renewal/revocation. Combined with the found "device-cap eviction never revokes Pro" bug, entitlement staleness is worse than the finding states: even a legitimately cancelled/refunded subscription stays "Pro" until the device happens to re-auth. Nobody audited webhook infrastructure as a missing surface, only the eviction logic on top of it.
>
> **Widget extension surface unaudited.** `ios/SnapWorthWidgets` contains `QuickScanWidget`, `HaulWidget`, a Live Activity, and a Control widget — real code paths (App Group data sharing, background refresh cost, a widget-triggered scan potentially bypassing the same App Attest/quota flow as the main app) that only get one mention, in passing, on the privacy-manifest finding. None of the widget's own logic was read.
>
> **The ideas list never proposes fixing the bugs the same audit just found.** All 15 scored ideas are growth/UX features; none targets the two high-severity, single-file, small-diff bugs (App Attest permanent lockout, 402→paywall routing) that block the very "reason-aware paywall" and "don't interrupt the free-scan experiment" ideas ranked #1 and #4 — those ideas literally cannot work correctly until the routing bug is fixed, but the fix itself isn't scored or listed.
>
> **Paid path is structurally unverified.** Business state says 0 paid subscribers; `StoreKitPurchaseService`/entitlements code exercising a real (non-comped, non-sandbox) purchase-to-entitlement round trip has never actually run in production, and no finding flags that the paid flow is code-reviewed but not yet field-proven.

Note on the third point: this pass's §1 does now include `NotificationManager`/App-Group-adjacent findings (I-20) beyond the privacy-manifest mention, but the widget extension's own scan/refresh/attestation-bypass logic is still genuinely unread — the critic's core point stands.
