# SnapWorth audit — September 2026

**Date:** 2026-09-03 · **Base:** `0809f34` (main after PR #81) · **Scope:** `backend/`, `ios/`, `website/`, `marketing/`, `.github/`, the Telegram bot.
**Method:** direct source review, every finding cites a file. Backend suite run before and after (816 → 836 tests, all green). Nothing below is inferred from a README.

The previous audit (`docs/AUDIT-v2.md`, July) found three structural problems: screenshots claiming a data source that did not exist, four inert security controls, and an ungrounded AI layer. All three have since been addressed in the codebase — the screenshots were replaced (PR #79 kept them as shipped), App Attest is enforced, StoreKit environments are checked, subscriptions are device-bound, and the confidence score is computed from signals rather than self-reported. This audit is therefore smaller and more operational: what is wrong *now*, after six weeks of shipping.

## 1. Fixed in this PR

Each of these is verified by a test that fails on the old code.

| # | Finding | Where | Fix |
|---|---|---|---|
| F-1 | **The bot went silent after every deploy.** Only one replica may poll Telegram; the lock (`opslock:tgpoll`, TTL 90 s) was never released on shutdown, so the freshly deployed replica could not poll until the dead one's lock expired — and it only re-checked every 30 s. Up to two minutes per release of button presses that were read and never answered. This is the "it doesn't send me the deploy automatically, I have to refresh" report. | `backend/notify.py` `aclose`, `_command_loop` | `_release_poll_lock()` on shutdown (compare-and-delete, never another replica's lock); lock re-check every 15 s. |
| F-2 | **Commands could be answered twice after a failover.** Telegram confirms an update only when a *later* poll carries the offset past it. A replica that died right after replying left its batch unconfirmed, and the successor started from `offset=None`. | `notify.py` `poll_once` | The offset is persisted (`opsstate:tgoffset`) after each round and read at loop start. |
| F-3 | **The deploy ping had one shot, seconds into a boot.** One `sendMessage`, no retry; a cache error in the dedupe guard skipped the ping silently; a failed send still consumed the guard, so a restart of the same build stayed quiet. | `notify.py` `_announce_deploy` | Retries at 2/5/10 s; a guard failure sends anyway (a duplicate beats silence); a total failure hands the guard back. |
| F-4 | Telegram send failures logged only the HTTP status. A `400 can't parse entities` — the bug class most likely in HTML messages — was indistinguishable from anything else. | `notify.py` `TelegramNotifier.send` | Logs Telegram's `description` (it carries no token). |
| F-5 | The JSON-reformat model call (`_retry_as_json`) bypassed the token tally, so `/costs` and `model_tokens` under-reported exactly the scans that cost most. | `backend/main.py` | Counted as operation `reformat`. |
| F-6 | Instagram Graph API integration removed at the operator's request (Business account + Facebook Page + Meta app review + 60-day tokens was not worth the numbers). `/social` is TikTok only. `IG_USER_ID` / `IG_ACCESS_TOKEN` can be deleted from Railway. | `backend/social.py`, `notify.py`, `.env.example` | Subtraction only; the website's Instagram *link* stays — the account exists, the API reader does not. |
| F-7 | README described the free tier as "3 free scans"; it has been one a day since 1.2. A stale `TODO: Replace # with App Store link` comment sat above a link that was already correct. | `README.md`, `website/index.html` | Copy fixed, comment removed. |

## 2. Findings to act on — not changed here

Ordered by how much they matter, not by component. Each says why it was left for a human.

### A-1 · Privacy policy does not name its processors `[LEGAL COPY]`
`backend/main.py` `/privacy` says photos are "processed by an AI model" and that analytics uses TelemetryDeck, but never names **Google** (Gemini receives every photo) and does not mention that **item names and estimates** — never photos, never identifiers — reach the operator over **Telegram** via the live feed and `/finds`. "We do not … share your photos, device identifier, or analytics data with third parties" is true as written, but a reviewer reading it against the architecture would expect the processors listed. Proposed additions, under *How We Use Your Information*:

> Photos are transmitted to Google's Gemini API for analysis under Google's API data-use terms and are not used to train models. Aggregate operational information — the name of an item identified and its estimated price range, never the photo, never a device identifier — may be relayed to the operator through Telegram to monitor the service.

Left for the operator because it is legal text on the App Store listing's privacy URL.

### A-2 · Certificate pinning can never be turned on as designed `[iOS]`
`ios/SnapWorth/Config.swift` keeps `pinningEnforced = false` until "one full release has reported zero mismatches in the field". But `ios/SnapWorth/Services/CertificatePinning.swift:89` reports a mismatch only to `os_log` — which nobody can read from the field. The precondition is unobservable, so the flag will stay false forever. Fix: add an `Analytics` event (`certificate_pin_mismatch`, no payload beyond the host) and fire it from the report-only branch; after a release with zero events, flip the flag. Left because it is an iOS change I cannot compile here; it belongs in 1.3.5.

### A-3 · 1.3.4 is built in the repo but not in the App Store `[RELEASE]`
`MARKETING_VERSION = 1.3.4`, build 11, release notes and metadata in `marketing/RELEASE-NOTES-1.3.4.md` — all ready; the operator chose to wait a week. Until it ships, none of the following is live for users: Poshmark/Mercari/Depop listings, the Keychain device identity (the reinstall fix for #55), the new subtitle/keywords/promotional text (which must be pasted into App Store Connect with the submission — they do not deploy from the repo). Everything in A-4 waits on this.

### A-4 · Website copy names the old marketplaces only `[WEBSITE, AFTER A-3]`
`website/index.html` mentions eBay 19×, Vinted 14×, OLX 14×, Facebook Marketplace 10× — and Poshmark, Mercari, Depop 0×, although the ASO work made those the lead keywords. Do **not** change it before 1.3.4 is live: the site would promise listings the installed app cannot write. The day 1.3.4 is approved: meta description, the "Snap → Sell" feature copy and the FAQ.

### A-5 · Every unknown URL on the website is a 200 `[WEBSITE, SEO]`
`vercel.json` rewrites `/(.*)` to `/index.html`. `cleanUrls` already serves `/support` and `/worth/<slug>` without it, so the rewrite's only effect is that `/anything-at-all` returns the homepage with a 200 — soft 404s, which search engines treat as duplicate content across the 20 programmatic `/worth/` pages this site depends on. Remove the rewrite and add a `404.html` (Vercel serves it automatically). Left because I cannot verify a Vercel deploy from here.

### A-6 · Free-tier experiment lever is armed but unused `[GROWTH]`
`FREE_SCANS_FIRST_DAY` (PR #79) is `0` in Railway. The funnel measured 18.6 % product-page conversion but the in-app step from first scan to paywall is unmeasured. Recommendation stands: change one thing at a time — metadata first (needs 1.3.4 in ASC), then set `FREE_SCANS_FIRST_DAY=3` for a fortnight and read `free_scan_limit_hit → paywall_viewed → purchase_started` in TelemetryDeck.

### A-7 · `/metrics` has no reader `[OPS, ACCEPT OR ACT]`
`docs/RUNBOOK.md` §1 still says the collector is `[NOT IMPLEMENTED]`. Six weeks on, the Telegram bot has become the actual monitoring surface — provider health, spend, actives, deploys. That is a reasonable place to be for one operator. Either accept it and say so in the runbook, or point a free Grafana Cloud scrape at `/metrics` with `METRICS_TOKEN`. The Prometheus code is not wrong; it is unread.

### A-8 · Poll lock errs toward polling when the cache is down `[BOT, ACCEPTED]`
`notify._hold_poll_lock` returns `True` on a cache exception, by design ("a duplicated reply beats a bot that never answers"). With two replicas and Redis flapping, both would poll, Telegram answers 409 to both, and the bot is silent until Redis returns. Single-replica today, so moot; noted for the day a second replica is added.

### A-9 · Subscriptions table only knows what has synced `[BOT, BY DESIGN]`
`/subs` lists subscriptions seen since PR #76 deployed; each active one appears at its owner's next app launch. Apple's own list is the source of truth (App Store Connect → Subscriptions). The message says so.
