**Audited tree:** `main` at `d19f6e2` (1.5.3, build 23 bumped, not yet archived). Production runs `28e3dee`: the same backend, since `d19f6e2` only bumps the app's version.

**Method:** one reviewer, reading code and running it. The 2026-09-26 audit (106 findings, 12 auditors) is the baseline. Its top 10 and its backend Medium findings were re-checked against the code. The 303 commits since were reviewed by risk rather than line by line. That covers every HTTP route's authentication and limits, the token, App Attest, StoreKit and Apple-notification verification, sale sharing, referrals, the money shown in the ledger, and what the app stores. Both test suites were run, backend coverage was measured, the full git history was scanned for secrets and the backend dependencies were checked for CVEs. Production was read through its public `/health` only.

**Not covered:** a Simulator or device walkthrough (#229's is still the owner's), the website beyond the previous findings, the evaluation harness, and line-by-line review of `HaulSession.swift` and `ScanView.swift`.

## 2. Findings

### [Medium · S] M1. Flip totals add different currencies together and print them as US dollars

**New in 1.5.3** (`0c2049a`, #224 part 3a; not in `build-22`).

Before #224 every ledger amount showed `$`. Now a flip's own row shows its currency: the one the user picked, or the phone's region currency by default (`SaleCurrency.of`, `SaleSharing.swift:20-29`; `FlipLedgerSection.swift:135`, `:258-266`). Every total still adds the raw numbers across flips and formats them with `NumberFormatter.snapCurrency`, which is fixed to `USD`/`en_US` (`DesignSystem.swift:432-439`):

- Flips header: "Profit this month" and "Invested" (`FlipsViewModel.swift:177-180`, `:339-348`)
- The monthly profit bars (`FlipsViewModel.swift:225`)
- The month share card (`ShareCardView.swift:295-318`)
- The Home Screen widget (`WidgetDataStore.swift:30`)
- History's realized total (`HistoryViewModel.swift:141`)

**Failure:** a phone set to Romania, with no currency picked. The user marks a find bought for 20 and sold for 100. The row reads **+80 lei** and the header reads **+$80**. Add a flip sold in euros and the header adds lei and euros together as dollars.

A second effect: on every flip saved before 1.5.3 (`saleCurrency == nil`) a non-US user typed the amounts under a `$` label, and the row now relabels them in the region currency.

**Fix:** the totals need the currency the rows have. If every flip in a total has one currency, format the total in it. If they differ, show one total per currency rather than a sum. Converting with the ECB table is possible, but that table lives on the server. Decide what a legacy flip's currency is: keeping `USD` for `saleCurrency == nil` keeps what those users saw when they typed the amounts. Add a test with two flips in different currencies.

### [Medium · M] M2. The App Attest success path has never run in a test

`appattest.py` has 60% line coverage, the lowest of any backend module, and what is missing is the part that decides. Lines 192-247 of `verify_attestation` never run in a test:
- the nonce comparison
- the key-id ↔ public-key binding
- the app-ID (rpId) check
- the production/development environment check
- the zero-counter check

`verify_assertion`'s bad-signature branch (`:302-303`) never runs either. The tests feed only malformed inputs, which fail before any of these checks.

**Failure:** delete the line `if embedded_nonce != expected_nonce: raise …` (`:206`), or the `key.verify(…)` in `verify_assertion`, and all 2,226 tests still pass. Those few lines decide whether a request comes from a genuine copy of the app.

**Fix:** build a test chain with `cryptography` (a test root, intermediate and leaf carrying the nonce extension, plus an `authData` built to match). Let `_verify_chain` take the root as a parameter that defaults to Apple's. Then add one passing attestation and one test per check that tampers with exactly the field that check guards. Do the same for an assertion with a valid and a forged signature.

`tokens.py` (70%) misses only `signer_from_env`, which includes the production guard that refuses to start without `TOKEN_KEYS` (`:149-191`). That is worth a test too.

### [Medium · L] M5. "High confidence" is shown to every user, and nothing has measured what it means

The band's meaning is now written down (#314: High means the sale lands in the range shown, at least 70% of the time). But there is no gold set (`eval/data/gold.jsonl` does not exist), so:
- nothing has measured it
- the accuracy gate cannot fail (`Accuracy regression gate: skipping` on every PR)
- `EVALUATION.md` still says no measurement has been taken

That is the previous audit's "The accuracy regression gate can never fail", still open. **Until #213's gold set exists, no app, site or store copy should claim accuracy**, and none currently does. The blocker is the owner's: collecting verified sales.

### [Medium · S] M6. A burst of merges can leave production on an old commit, with nothing red

Found while merging #314–#318 on 2026-10-07; not in the original pass.

`backend.yml`'s deploy job was ordered only by its own concurrency group, `deploy-railway-production`, with `cancel-in-progress: true`. A job joins that group when its run's tests finish, so deploys were ordered by test duration, not push order.

**What happened:** #316, #317 and #318 merged within three seconds.
1. The newest commit's deploy uploaded.
2. While it was verifying, an older commit's deploy, queued after it, cancelled it.
3. That older deploy was cancelled in turn.
4. Production stayed on #315's commit for about 1h40m, until #319's push.

A cancelled run is grey, not red, so nothing said production had not moved.

**Fix (#321):**
- A workflow-level group for pushes to `main`, without cancel-in-progress: runs go one at a time in push order, and a newer push replaces any older run still waiting.
- Pull requests stay parallel.
- The deploy job's group no longer cancels.

### [Low · S] L1. A challenge can be redeemed twice by two concurrent requests

`_consume_challenge` (`auth.py:340`) reads the nonce and then deletes it, as two cache calls. Two requests racing on one nonce can both pass. The impact is small: an attestation is bound to its key and nonce, and an assertion's counter must advance. Use one atomic operation (`GETDEL`, or a delete that reports whether it removed anything).

### [Low · S] L2. A scripted install can drain the referral friend-code pool (dormant)

`_bind` (`referral.py:397`) ties a `device_id` to the first App Attest subject that presents it. But an access token is a one-hour bearer token, not bound to each request. A reinstall gives a new subject, and a script with that subject's token can claim with an invented `device_id`, getting one friend offer code per reinstall. Only the route's rate limit bounds it. Referrer rewards still need a different Apple ID for each "friend", so the cost is pool exhaustion: genuine friends get "Invites are paused". **Dormant until `REFERRALS_ENABLED`.**

Before switching it on, watch the pool's `/referrals` level and the claim-to-redeem ratio. Consider a per-IP daily cap on `claim`, or requiring a DeviceCheck token on claim and one claim per device bit.

### [Low · S] L3. Sale-sharing fields that should be from fixed lists accept any short text

`outcomes.py:95-102`: `category` (40 characters), `condition_grade`, `condition_chosen`, `prompt_version` and `confidence_band` take any text. The privacy promise, "never the item's name", is kept by the app, not the server. A modified client could store free text there, and the export would pass it on to `eval.cli field`. Restrict each one to the values the app sends (`categories`, the condition grades, `High|Medium|Low`).

### [Low · —] L4. One shared subscription keeps up to six devices Pro at a time (accepted)

By design (`entitlements.py`, `_bind_device`): eviction instead of refusal, so a payer is never locked out. Churn raises `subscription_over_cap`. Recorded so the decision stays visible. Revisit if the over-cap alert fires often.

### [Low · S] L5. Certificate pinning is configured but not enforced

`Config.swift:79` `pinningEnforced = false`. Unchanged since the previous audit's "The certificate pin set is not ready for enforcement". It also makes L2 easier, since a user can read their own token through a local proxy.

### [Low · S] L6. 43 iOS tests check source text rather than behaviour

43 of 1,113 test functions open a `.swift` file and assert that it contains a string, for example `test_onlyTheScanSheetIsFresh` (`ProductionHardeningTests.swift:4387`). They pin wording, so a pure move breaks them while a behaviour change that keeps the wording passes. #229 replaced the five on `ResultView`; the rest are on `ScanView`, `PaywallView`, `SettingsView`, `HistoryView`, `FlipsView` and `HaulView`.

### [Info] I1. Certificate validity is checked against today, not the transaction's signing date

`entitlements.py:403`. This is stricter than Apple's own library. It only matters for a stored proof re-verified after its leaf certificate expires, which the proof store's own expiry makes unlikely. No action needed; noted for whoever reads this code next.

### [Info] I2. `notify.py` still turns off one pyright check for the whole file

`notify.py:68`. #230's acceptance covers only the new modules, which need no suppression. After steps 6–8 (#316–#318) `notify.py` is 2,667 lines and still the file most likely to hide an Optional access.

## 3. What was checked and holds

- **Routes.** Every route is authenticated or deliberately public:
  - Authenticated through `require_auth`: `/scan`, `/listing`, `/trends`, `/auth/entitlement`, `/outcomes`, `/referral`.
  - The three pre-token routes (`/auth/challenge`, `/attest`, `/refresh`) are IP-rate-limited.
  - `/metrics` takes a bearer token.
  - Apple's notification routes accept only a signed body.
  - TikTok's OAuth callback checks a single-use `state` and echoes no input.
- **Production enforces App Attest:** `/health` says `auth_enforcing: true`. The legacy path, where `x-device-id` is the caller's choice, is closed there. Redis and the distributed rate limiter are healthy.
- **Tokens:** each request re-reads the entitlement rather than trusting the token's tier. A Redis outage keeps a verified tier for the token's hour, and a Sandbox tier is read as free during one. Attest and refresh use `required` cache reads wherever a failure could otherwise mint a new subject.
- **StoreKit and Apple notifications:**
  - the chain must end at Apple Root CA G3 and pass date, CA-flag and signature checks
  - Apple's purpose OIDs on the leaf and intermediate are required
  - only ES256 is accepted
  - Sandbox purchases are admitted only for an App-Attested caller, on bounded terms
  - the refund tombstone needs Redis
  - `REFUND_REVERSED` lifts the tombstone
- **`/scan` ordering:** rate limits, then the quota reservation, then validation (refunded on failure), then a disconnect check (refunded), then the model. The body cap counts streamed bytes, which fixes the previous audit's only High finding (`main.py:701-776`).
- **Sale sharing (`outcomes.py`):**
  - the model refuses unknown fields
  - attested callers only
  - a per-device limit plus a daily cap
  - only the install that created a record can replace or delete it
  - the token is stored as a keyed hash, and the export drops it
- **Trending:** a name reaches other users only once enough distinct devices stand behind it (`trends.py`, `min_devices`).
- **iOS:**
  - the access token and device id are in the Keychain
  - no token or signed transaction is logged
  - every authenticated call uses `requireBearerToken`, which never sends a request without a token
  - the privacy manifest declares Purchase History and Other Financial Info
