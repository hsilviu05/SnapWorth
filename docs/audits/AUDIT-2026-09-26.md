# SnapWorth audit, 2026-09-26

**Method:** 12 independent auditors (iOS state, iOS UX/l10n, StoreKit/App Review, iOS security, backend security, backend reliability, AI pipeline and economics, performance, website, CI/DX, tech debt, product), each finding challenged by adversarial refuters (two per high/critical, one batch pass for the rest), then deduplicated, a completeness critic and four gap audits. 111 findings raised; 8 refuted outright and most severities corrected down. Audited tree: `main` at 22865a3.

**Scope:** 92 merged findings and 14 gap findings, 106 in total: 1 high, 44 medium and 61 low. No gap finding duplicates a merged one. Where two findings touch the same code, the text points to the other. The gap findings had no area, so each one is placed in an area by the files it touches. All severities are as given in the inputs.

**Path key:** `main.py`, `auth.py`, `quota.py`, `notify.py`, `entitlements.py`, `cache.py`, `referral.py` and the other `.py` files are in `backend/`. Swift files are in `ios/SnapWorth/**`, and widget files are in `ios/SnapWorthWidgets/`. `index.html`, `support.html`, `invite.html` and `guess.html` are in `website/`. Workflows are in `.github/workflows/`. `RUNBOOK.md`, `AUDIT-*.md` and `EVALUATION.md` are in `docs/`. Listings and release notes are in `marketing/`.

## 2. Findings by area

### iOS (36)

#### [Medium · S] The yearly 'SAVE 33%' badge never appears
- **Evidence:** StoreKitPurchaseService.swift:320-327 turns an unrounded Decimal ratio (33.2164…) into an Int with `.intValue`, which returns 0, so `savingsPercent` is nil. PaywallView.swift:62-63 then falls back to 'BEST VALUE'. The shipped prices are at SnapWorth.storekit:32/60. The tests either pass nil (ProductionHardeningTests.swift:827) or hardcode 33 (MockPurchaseService.swift:29). The function is unchanged since 1f13424.
- **Impact:** The yearly plan is preselected and is the only plan with the trial, yet it never shows its saving in any storefront. The website advertises 'Save 33%' (index.html:2223). This loses conversions; nobody is charged wrongly.
- **Fix:** Round with `NSDecimalRound(..., 0, .down)` before `.intValue`. Pull the maths out as a `nonisolated static` function and test that 39.99/4.99 gives 33 and 44.99/5.99 gives 37.

#### [Medium · S] An Action Button press while the app is open leaves a pending scan request
- **Evidence:** AppIntent.swift:33-34 writes the App Group request and also opens `snapworth://scan`. The comments at AppIntent.swift:20-24 and commit 8b5c377 say whichever channel arrives first consumes the request, but the URL handler at SnapWorthApp.swift:185-187 never calls `WidgetBridge.takePendingAction()`. The only caller is `drainPendingWidgetAction` (SnapWorthApp.swift:166-181, call at :175), which runs from `.task` and on the move to active (:120-125). The request lives for 5 minutes (WidgetDataStore.swift:631). When it drains, ScanView.swift:411-418 runs.
- **Impact:** For 5 minutes after the press, any inactive-to-active change drains the stale request: locking and unlocking the phone, pulling down Notification Centre, or the StoreKit sheet closing. The drain closes the result sheet, closes Thrift Flip (losing the typed prices), or closes the paywall mid-purchase. The scan itself is already saved.
- **Fix:** Call `_ = WidgetBridge.takePendingAction()` in the `scan` case of `handleWidgetURL`. Add a test that a URL-driven scan leaves nothing pending.

#### [Medium · S] The default 'Result card' share image has no 'estimate' label
- **Evidence:** ShareCardView.swift:139-179 draws `formattedRange` at 50-56pt with no qualifier anywhere on the card (body at :84-135). The guess card on the same canvas does label it (:510-520, per d1ff366). The in-app value card says 'AI estimate' (ResultView.swift:802). 'Result card' is the first choice in the share dialog (ResultView.swift:216). The card dates from 2d84b2f, before the 341c786 copy-honesty pass.
- **Impact:** The one image built to leave the app reads 'Paid $8 → $45–$90 · 5x find' under the SnapWorth brand and QR code. A viewer takes that as what the item is worth or sold for.
- **Fix:** Add `Text('AI resale estimate')` under the range in both hero branches (the key is already in App.json). Use 'estimated' in the badge accessibility labels.

#### [Medium · S] The hero condition chip shows cut-off fragments
- **Evidence:** ResultView.swift:642-651 splits `conditionNotes` on '—–-.' and keeps the first 22 characters (`.prefix(22)`). That was written for v1 notes (prompts.py:62). v2 is now the default (prompts.py:160) and writes prose (prompts.py:125), so the chip shows 'Well', 'Pre' or 'Moderate fading throug'. It also ignores `result.condition`.
- **Impact:** Most results since v2 put a garbled English label on the hero photo in all five languages. The label can contradict the Condition the user chose.
- **Fix:** Show `result.condition.label` in the chip. Keep the full notes in the Condition details card.

#### [Medium · S] The weekly portfolio notification counts sold items but values only held ones
- **Evidence:** NotificationManager.swift:605-617 uses `itemCount: results.count`, which includes sold rows, next to a total that covers held items only (HistoryViewModel.swift:132-145). The body is built at NotificationManager.swift:586-600. Commit c39c8f2 changed the total but not the count. MigrationTests.swift:617-625 checks only the money.
- **Impact:** A user who sold 4 of 10 finds is told 'Your 10 finds are worth $120' when the $120 covers 6. A user who sold everything is told 'Your 10 finds are worth $0'. The notification is on by default and fires Sundays at 11:00.
- **Fix:** Count only rows that are not sold, and send nothing when that count is 0. Make the test at MigrationTests.swift:617 assert 'Your 1 find is worth'.

#### [Medium · S] The 'Notifications are off' banner sends never-asked users to a Settings page with no switch
- **Evidence:** NotificationSettingsView.swift:135 treats `.notDetermined` as denied. The banner (:24-45) can only open Settings (:27). Tapping 'Not now' on the priming screen leaves the status at `.notDetermined` for good (NotificationManager.swift:236), and iOS shows no switch for an app that never asked. The toggles already read ON (`defaultEnabled`, NotificationManager.swift:68), so the in-screen permission request (NotificationSettingsView.swift:115-121) never fires. The reasoning in 4499251 is wrong, because declining the system alert gives `.denied`.
- **Impact:** The users this banner was written for (see the comment at NotificationManager.swift:169-183) find nothing to switch on. They keep getting no notifications, including the reminder that a trial is about to end.
- **Fix:** For `.notDetermined`, show 'Allow notifications' and call `requestAuthorizationIfNeeded()`. Deep-link to Settings only for `.denied`. Replace the string-presence test with a behaviour test.

#### [Medium · S] attachBearerToken still falls back to an upload without a token
- **Evidence:** TokenStore.swift:204-218 swallows token-mint errors 'during rollout', and ScanAPIClient.swift:421-423 (now ~480-481) has the same comment. Production now requires App Attest (`auth_enforcing: true`, auth.py:423-429; AppError.swift:79; Config.swift:12-14). `fetchChallenge` (AttestationService.swift:236-243) reduces a 429 to a generic `challengeFailed`. `sendRetryingAuth` (TokenStore.swift:240-249) then returns the 401, which AppError.swift:174 maps to `.sessionExpired`, telling the user to reinstall (AppError.swift:84). When offline, `waitsForConnectivity` with a 35 s limit (CertificatePinning.swift:211-212) runs twice.
- **Impact:** Offline with an expired token, 'Analyzing…' runs for about 70 s. A rate limit or an Apple outage tells the user to reinstall, which fixes neither. Each failure uploads the photo only to get a certain 401. A subscriber whose attestation fails is counted as free and gets a 402 and the paywall.
- **Fix:** When `Config.useAttestation` is on, use a throwing `requireBearerToken()`. Map URLError to network or timeout errors, and a 429 to a rate-limit error with its Retry-After (keep the HTTPURLResponse). Show 'couldn't verify' only for a real rejection. Remove the rollout comments and the `x-device-id` header, which only auth.py:432 reads.

#### [Medium · S] The rating prompt fires 1.2 s after a fresh result opens, while the price is still covered
- **Evidence:** ScanViewModel.swift:146-150 waits 1.2 s and then calls `ReviewPrompt.recordSuccessfulScan()`. ScanView.swift:553-556 opens a result whose price is still covered (`coverPrice: true` at ScanView.swift:499; `GuessFirst.defaultOn`). ReviewPrompt.swift:18 and :29-30 ask once lifetime scans reach 3, and again on every new version. The delay predates the price cover (2eedaa5; 417fda3). There were four version bumps between 09-14 and 09-25.
- **Impact:** After every update, engaged users are asked to rate the app before they see the price they scanned for. iOS allows only 3 prompts a year, so the budget is spent at a moment with no payoff. Ratings feed a search card that converts at 2.1% (app_store_listing.md:19-22).
- **Fix:** Ask from ResultView after the price is revealed, and only for Medium or High confidence; 'Mark as sold' is another good moment. Replace once-per-version with a minimum gap of 60 days or more. Add a `review_prompt_requested` event.

#### [Medium · S] 'Why this price' shows backend enum tokens as display text

The mocks use prose instead of the real tokens (ScanAPIClient.swift:328, :330).

- **Fix:** Add client enums with localized labels: AuthenticityRead, `Condition(serverGrade:)?.label`, and demand/supply adjectives. Drop unknown tokens instead of printing them. Switch the mocks to the real tokens and add a test that no displayed string contains `_`. Use a neutral icon on the confidence reasons (ResultView.swift:1547), because the server sends the weakest signals there (confidence.py:280).

#### [Medium · S] VoiceOver cannot reach 'Unlock value history' or hear the insight line

#### [Medium · S] 'Your free scan is back' is scheduled by local day, but the allowance resets at UTC midnight
- **Evidence:** The allowance counts UTC days (ScanViewModel.swift:366-382; quota.py:99-100; Config.swift:91; WidgetDataStore.swift:495-503, :579-587). The reminder uses `Calendar.current` (NotificationManager.swift:497-505), and its inputs are local-day flags (ScanViewModel.swift:338-344; NotificationManager.swift:559; NotificationSettingsView.swift:142). The default time is 18:00 (NotificationManager.swift:435) and the body is at :535. The reminder is opt-in (NotificationManager.swift:68).
- **Impact:** A user on US Eastern time who scans at 21:00 is told at 18:00 the next day that the free scan is back. Tapping it opens the paywall, because the scan actually returns at 20:00. Users east of UTC miss reminders on days the allowance has already reset. The reminder also disagrees with the Scans-left widget.
- **Fix:** Never fire before the next UTC reset after the last scan. Take `scannedToday` from FreeScanCounter's UTC stamp, and reuse `serverCalendar`. Add tests in America/New_York and in a UTC+10 zone.

#### [Medium · S] The privacy manifest does not declare Purchase History
- **Evidence:** PrivacyInfo.xcprivacy:9-103 has no PurchaseHistory entry, and git history shows it was never considered. The app captures Apple's signed transaction (StoreKitPurchaseService.swift:346) and uploads it on every refresh (:379-381) with the device ID (AttestationService.swift:61-72). The server keeps it for 400 days (entitlements.py:77-86) and links devices through `original_transaction_id` (:532). Neither privacy policy mentions this (LegalView.swift:45-70; main.py:1222+).
- **Impact:** The manifest and the App Store label under-declare what is collected (Guideline 5.1.2), and 'not linked' for Device ID is debatable. Rejection risk is modest; the EU transparency gap is the bigger concern.
- **Fix:** Declare PurchaseHistory with purpose AppFunctionality and no tracking, and decide Linked honestly. Update the App Store Connect label to match, add one sentence to both policies, and extend the manifest test.

## 4. Strategic recommendations

1. **Make the paid path work end to end before the next offer goes to review.** Nine findings fail on the same path from purchase to server entitlement to support:
   - production rejects Sandbox, so App Review purchases don't unlock Pro
   - a StoreKit-Pro, server-free split sends subscribers to the paywall
   - the panel that sold the upgrade is empty after purchase
   - the refund tombstone isn't a required write
   - REFUND_REVERSED is ignored
   - /sub can't use the ID in a support email
   - /checkup doesn't cover the App Store key or notifications
   - `attachBearerToken` turns attestation failures into 402s
   - the scan-limit paywall discards the photo

   Add two end-to-end tests: 'a reviewer buys in Sandbox, then scans, drafts a listing and opens Why this price', and 'refund, then reversal'.

2. **Treat Redis as a system of record, and watch it from outside the process.** Refund tombstones, attest state, the experiment lever, referral codes and the operator indexes now exist only in Redis. Yet the RUNBOOK calls it a disposable cache, no persistence, memory limit or eviction policy is confirmed, some writes that gate money silently fall back to memory, whole documents can be overwritten after one failed read, and no alert fires when Redis or the API goes down. The fixes:
   - confirm AOF persistence and set `noeviction` with a memory limit
   - make every write that gates money `required=True`
   - move read-modify-write documents to hashes
   - add an external probe and cache alerts
   - rewrite RUNBOOK §1/§9 and §5.4

3. **Make the server–client contract explicit, typed and versioned.** Today the contract fixture is Pro-only and untyped, the server can't see which build is calling, errors and confidence reasons are English prose with no code, enum tokens are printed raw, and the category list exists in 8 drifting copies. Do it in this order:
   1. real fixtures with field types, including the free and error shapes, and the README rule that a type change is breaking
   2. codes beside the prose (`code`, `confidence_reason_codes`) in new fields, with localized maps on the client
   3. a build header and a minimum-build switch
   4. one category table on each side

   Adding codes is exactly the kind of type change that would break every installed build if it went in first.

4. **Do one truth-in-copy pass across policy, store, site and app, then enforce it in CI.** The findings:
   - the privacy retention statement is false
   - the support page contradicts the policy it links to
   - the manifest omits Purchase History
   - the policy lacks the GDPR basics
   - the homepage sells a free feature as paid
   - the store listings are English-only with a different name
   - the 'accurate' claim is unmeasured
   - the share card has no 'estimate' label
   - onboarding promises 'exact profit'
   - demand and supply are shown as fact
   - the site names 'seven' marketplaces and says 'confidence score'

   Fix them in 1.5.1 and on the site. Update `website/` in the same commit as any change to a gate. Add CI checks in the style of `check_homepage_ranges.py` (fees, marketplace list), and make them required through a main ruleset, since every check is advisory today.
