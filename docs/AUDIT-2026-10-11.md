# SnapWorth audit, 2026-10-11

**Audited tree:** `main` at `50a4184` (1.5.3, build 23 bumped, not archived). Production ran `e3f61db` once #331 merged.

**Method:**
- 13 reviewers each read one area in depth: iOS scan, Haul, purchases, data and ledger, widgets and notifications, result sheet, app and privacy, compliance and localization; backend scan, auth, money, data and ops; website and CI.
- 3 earlier reviewers covered the 1.5.3 diff: sale sharing, currency, and the ResultView split.
- 60 raw findings were merged into 53.
- Each finding was then checked by independent skeptics told to refute it, each from one angle:
  - **trace:** does the claimed code path actually happen?
  - **intent:** is it deliberate, already guarded, or already fixed?
  - **impact:** can a real user or attacker reach it?
- A finding counts as confirmed only when two of them agree. 44 were confirmed and 1 was refuted. The 7 earlier-reviewer findings (ids 44–50) were not fully verified; each was re-checked in the code before it was fixed.
- No Swift was compiled here. Every iOS fix went through CI (`xcodebuild test`).

Yesterday's audit (`AUDIT-2026-10-07.md`) was the baseline. Nothing it lists as fixed, accepted or owner-only was re-reported.

## 1. Verdict

**One High, live in production:** App Attest assertions were verified over the wrong digest (finding 35).
- Every genuine `/auth/refresh` was rejected, so the app re-attested as a new subject.
- With DeviceCheck's reinstall bit set by an exhausted day, that new subject started with no free scans.
- It went unnoticed because the tests signed the same wrong way the code verified. The verifiers confirmed the bug against a real device's assertion.
- **Fixed in #331 and deployed 2026-10-11.**

**One High in the 1.5.3 build:** `willPresent` and `didReceive` were the `nonisolated async` variants, so a notification tap completed off the main thread (finding 17). **Fixed in #333.**

Everything else is Medium or Low. Nearly all of it is new in 1.5.3 (currency, sale sharing) and never shipped. **Every confirmed finding is fixed in `main`**, with the partial fixes and known gaps listed in §3.

## 3. Partial fixes and known gaps

- **18 (deep links over an open sheet):** routes now close the sheets on top. The Haul screen is left open on purpose: closing it would end the haul or stop a capture in progress.
- **19 (Scans-left widget):** refreshed on every 402. The token-mint update in `AttestationService` still changes the count without refreshing the widget, because it has no model context to do it with.
- **26 (digest after a delete):** Clear history cancels the digest, and since the follow-up deleting one find rebuilds it from what is left.
- **38 (refund tombstones):** a second refund merges into the first. Two refunds for one subscription processed in the same instant can still race; closing that needs a compare-and-set the cache doesn't offer.
- **3 (shared-sale index):** deletion always finds its records. An edited record can drop out of the export.
- **39 (contributor tag):** now an HMAC under a fixed key rather than `AUDIT_SALT`. Any test records shared before the change are orphaned.
- **44 (legacy flips):** a read-time rule, not a migration. A flip with amounts but no stored currency reads as USD, and nothing in the store is rewritten. It holds only while every writer of an amount also pins its currency, which today every one does.

## 4. Refuted

- **Per-device daily activity markers kept 35 days** (`notify.py:1451`, `opsseen:d:*` and `opsseen:fd:*`): not confirmed by two verifiers. One rated it a low-severity data-minimisation and disclosure gap: the markers are pseudonymised and operator-only, and nothing reads them after the day they de-duplicate. `opsindex` `pro_days` (30 days) is in the same position.
  - Left as is. Worth a line in the privacy policy, or a TTL of a day or two, when either is next touched.
