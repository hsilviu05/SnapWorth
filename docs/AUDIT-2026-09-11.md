# Audit — 2026-09-11

Scope: the whole repository. Backend (FastAPI, ~60 modules), iOS app (58 Swift
files, ~18k lines), website (22 HTML pages, two generators), CI and deploy
config. Ran the backend suite, pyright, and a link/accessibility pass over
every page; read the support-email path end to end because it was the one
thing asked for by name.

The short version: this codebase has been audited hard and it shows. The
defect classes an audit normally harvests are simply absent — no bare
excepts, no unsafe unwraps, no broken links; see
[Verified clean](#verified-clean). What it *did* turn up clusters in two
places, and both are places nobody had had reason to look at twice:

1. **The support email.** The app could not reliably send one, had three
   separate ways of losing the message, and when one did arrive the
   operator's own tooling could not act on it. (E-1 to E-6, E-8.)
2. **Colour, on the two pages nobody visits much.** `support.html` and
   `404.html` never received the WCAG corrections `index.html` got, so nine
   places on them sat under AA — one at 1.87:1. Adding a dark theme is what
   surfaced it: the work of separating text tokens from surface tokens meant
   reading every colour on every page. (E-10 to E-12.)

The rest — security headers, a stale doc reference — is small.

## Fixed in this branch

### E-1 · The Send button was inert on any iPhone with no mail account — high

`FeedbackView.sendFeedback()` ended in:

```swift
UIApplication.shared.open(url) { success in
    guard success else { return }
```

`open` reports failure when there is no app registered for `mailto:` — no
mail account configured, Mail deleted, or a managed device with it
restricted. The completion swallowed that. The user tapped **Send Feedback**
and *nothing happened at all*: no error, no state change, nothing to
distinguish it from a message that went through. Every retry did the same.

This is the whole of "email messaging is broken": for an affected user there
was no working channel to reach support, and no reason for them to suspect
the app rather than their own message.

**Fix.** The failure now renders a card that names the cause, shows
`Config.supportEmail`, and offers one button that puts the message *and* the
address on the clipboard — so the user's typing survives a route the app
cannot open.

### E-2 · The message was destroyed on a draft the user never sent — high

On `success` the old code ran `self.message = ""`. But `open` succeeding
means Mail *presented a compose sheet*, not that anything was sent. Anyone
who read their draft and backed out lost up to 500 characters with no undo
and no copy anywhere.

**Fix.** The draft is no longer cleared. The confirmation now reads "Your
draft is open in Mail — send it there", which is both true and the reason
the text is still on screen.

### E-3 · `+`, `&`, `=`, `?` and `#` corrupted or truncated the body — medium

The body went through `URLComponents.queryItems`, which does not
percent-encode `+`. A mail client decoding a query component turns a bare
`+` into a space, so `iOS 26 + widgets` arrived as `iOS 26   widgets` and a
phone number lost its country code. The delimiters were worse: an unescaped
`&` or `#` ends the `body` field, silently dropping everything the user
wrote after it — exactly the kind of detail a bug report is made of.

**Fix.** `SupportMail.composeURL` encodes each value against
`urlQueryAllowed` minus `+&=?#`. `SupportMailTests` round-trips a body
containing all five.

### E-4 · Bug reports carried no version, OS or device — medium

Nothing in the email said what it was about, so the first reply was always
"what version are you on?". Worse, the operator's own tooling was unusable
from it: `notify.py`'s `/user <id>` command is documented as being "for
answering a support email", and the email contained no id of any kind.

**Fix.** `SupportMail.diagnostics` appends app version, build, OS version and
the hardware machine identifier (`iPhone17,2` — `UIDevice.model` is the
string "iPhone" on every iPhone ever made). Deliberately nothing
identifying: no vendor id, no address, nothing the App Store does not
already report. A test asserts the block contains no `@` and never the
`identifierForVendor`. The `/user` gap that made this half a fix is E-8.

### E-5 · The support address was typed out in four Swift files — low

And that is not hypothetical: per `marketing/RELEASE-NOTES-1.3.4.md`, PR #59
moved the website and backend to one address and left the app pointing at
another, shipping the drift. Now `Config.supportEmail`, referenced by
`FeedbackView` and both `LegalView` sections.

### E-6 · `SettingsViewModel.sendFeedback()` was dead — low

Nothing called it; `SettingsView` navigates to `FeedbackView` instead. It
carried a second, hand-percent-encoded copy of the same `mailto:`, so it was
also a second place to forget. Deleted.

### E-7 · No security headers on the website — low

`vercel.json` set only a font cache rule. Now `X-Content-Type-Options`,
`Referrer-Policy`, `X-Frame-Options` and a `Permissions-Policy` that denies
camera, microphone and geolocation, on every path.

Genuinely low, and worth saying why rather than overstating it: the site
loads nothing third-party, posts no form, and stores nothing. No CSP,
because the pages carry inline `<script>` for the price calculator and the
guess game, so a useful policy needs per-build hashes and there is no build
step to generate them. (Note: `vercel.json` rejects unknown keys, so this
reasoning cannot live in the file.)

### E-8 · A support email could not be traced to a device — medium

`notify.py`'s `/user <id>` takes "the id column from `/users` or `/subs`" —
`auditlog.pseudonymise(subject)`, i.e. `sha256(SALT + subject)[:16]`. The
salt is server-side, so the app cannot derive its own id, and the email
carried none. The command documented as being "for answering a support
email" was unusable from one.

**Fix.** `TokenResponse` gained `support_id`, set from the function the
indexes are already keyed on. The client decodes it as *optional* — a build
can outrun the deploy that starts sending it, and an absent id must degrade
to "no id" rather than fail the mint that carries the access token — stores
it, and `SupportMail.diagnostics` appends a `Device <id>` line when there is
one. `reset()` clears it, since it describes an attestation identity that
call is discarding.

Not a credential: a salted truncated hash of a subject the client already
holds, which authenticates nothing. `contract/` did not need updating — it
covers `/scan` only. Four backend tests pin the value, its stability across
mints, and that it does not contain the subject; five iOS tests cover the
present, absent and empty cases.

### E-9 · The contract README named a CI job that has never existed — low

`contract/README.md` rule 3 pointed at a `contract-check` job in
`.github/workflows/contract.yml`. There is no such file. The *effect* is
real and correct — `backend.yml` and `ios.yml` each carry `contract/**` in
their own `paths` filter, so a commit touching only the contract runs both
suites — but the document sent you looking for a file that isn't there.
Corrected to describe the path filters.

### E-10 · The website was light-only, and a token swap could not fix it — medium

No `prefers-color-scheme` and no `color-scheme` in 1,457 lines of CSS, so
every page was a bright slab on a dark-mode device and the browser could not
style form controls correctly.

The obstacle was not the theme, it was that three tokens each did two jobs:
`--dark` was the primary text colour (21 uses) *and* the background of the
dark bands (6); `--dark2` was body copy and the featured plan's background;
`--white` was text on dark bands and the fill of raised cards. Under a theme
switch each pair moves in opposite directions, so the roles are separated
first — `--ink`/`--ink-2`, `--band`/`--band-2`, `--surface`, `--on-band` —
and `--terra-fill` is split from `--terra-text` for the same reason: white on
the lighter brand tone is 3.39:1, so a fill carrying white text cannot
lighten even when the text tone does.

Every dark value was checked against every surface it can land on; the lowest
in the palette is `--text-muted` on `--surface` at 5.41:1. Two things
deliberately do not invert, both confirmed by rendering: the iPhone mockup
(a picture of the app's light UI — the tokens are pinned back to light on
`.iphone-screen`, which inherits to the `.pf-*`/`.sd-*` rules drawn inside
it) and the hanging price tag and Product Hunt badge, which are objects on
the dark hero rather than surfaces of the page.

The 18 `/worth` pages and `/guess` are generated, so the change is in
`seo/build_seo.py`'s shared STYLE, not in their output.

### E-11 · Two pages never received the AA colour corrections — medium

`index.html` was corrected to `--warm-gray: #6E625B`. `support.html` and
`404.html` still carried `#8B7B75` — **3.79:1 on `--bg`, under AA's 4.5:1** —
in nine places between them. `support.html` also declared
`--text-muted: #A89990` at 2.58:1 (never read, so removed rather than
corrected), and its footer painted links at `rgba(255,255,255,0.3)`
(**2.69:1**) and the copyright at `0.2` (**1.87:1**), where index.html's own
footer uses 0.55/0.5 for 6.13:1 and 5.27:1.

Also: `::selection` was `--terracotta` under white — 3.39:1 — on every page;
the focus ring was a hardcoded `#D96C47` that could not follow the theme; and
`support.html` and `404.html` had no `:focus-visible` rule at all.

### E-12 · In-page anchors landed under the fixed nav — low

`html` had `scroll-behavior: smooth`, `nav` is `position: fixed` and ~68px
tall, and index.html has three in-page anchors (`#how-it-works`, `#pricing`,
`#thrift-flip`). Each one scrolled its own heading behind the nav bar. One
`scroll-padding-top` on `html` fixes all three; `scroll-margin` on each
section would have been three places to forget.

## Open — needs a decision, not just a patch

### A-1 · Nothing type-checks the backend in CI

`pyrightconfig.json` exists, but `.github/workflows/` runs only pytest,
pip-audit and a Docker build. Pyright currently reports **299 errors**.

I checked the ones that are not in tests and not the `notify.py` pattern:
`main.py:1184` and `ideas.py:367` are both false positives (the first is
inside a `try/except Exception` that catches the `AttributeError`; the second
is pyright failing to narrow across two `dict.get` calls). The 99 in
`notify.py` are one shape — `Optional` client attributes guarded by an early
return in a different function.

So: no live bug, but 299 errors is the same as no signal. A real
`None`-dereference would land in that noise unnoticed. Either add a gate
with a baseline, or narrow the `notify.py` pattern once and gate on zero.

### A-2 · The public support address is a personal Gmail

`her.silviu.i@gmail.com`, in 17 places including the App Store listing. Not
a bug, and Apple accepts it. But it is a personal inbox on the App Store
page, it cannot be handed to anyone else, and it has no shared history. A
domain address on `snapworth.eu` forwarding to the same inbox costs nothing
and changes one constant plus the listing copy.

## Verified clean

Stated explicitly because the absence is the finding — this is where an audit
usually spends its time.

**Backend.** 1,090 tests pass (14s), four of them added here. No bare `except:`, no mutable default
arguments, no `datetime.utcnow()`, no `assert` outside tests, and no
`eval`/`exec`/`pickle.loads`/`yaml.load`/`shell=True` anywhere in
non-test code.

**iOS.** No unsafe unwrap in shipped code. Every `try!` is inside a
`#Preview`; the one `as!` is the standard `layerClass` downcast in
`CameraManager`; the one `fatalError` is a documented last resort after an
in-memory `ModelContainer` fallback has already failed.

**Website.** 0 broken internal links across 22 pages (checked against
Vercel's `cleanUrls`, which is what makes the extensionless hrefs resolve).
`alt` on all 4 images. Exactly one `<h1>` per page. `prefers-reduced-motion`
honoured in both directions. All five page types render clean in both colour
schemes under Chromium, with no undefined or unused token on any page. Colour tokens carry
their measured contrast ratios in comments, with separate AA-compliant
variants (`--terra-text`, `--sage-text`) for text on brand fills. Zero
third-party requests — fonts are self-hosted — so there is nothing to leak
and no cookie banner to need. The sitemap's 20 URLs all resolve.

## Known limitations of this audit

* **No iOS build or test run.** There is no Swift toolchain on this Linux
  runner, so every iOS change here is verified by reading and by the unit
  tests added for it; CI on `macos-15` is the first thing that actually
  compiles it.
* **iOS review was static.** No simulator, so nothing about runtime
  behaviour, layout at Dynamic Type sizes, or VoiceOver order was observed.
* **The website was rendered, the app was not.** Chromium is available here,
  so every page was checked in both colour schemes at 1280px. Nothing was
  checked at phone width, and contrast was computed rather than measured off
  the rendered pixels.
  E-1 in particular is reasoned from `UIApplication.open`'s contract, not
  from a device with no mail account.
* **The widget extension was not read.** Same gap the 2026-09-07 audit
  closed with a note and did not fill.
* **Backend review was breadth-first.** Defect-class sweeps plus the full
  suite, not a line-by-line read of the comps engine or the entitlement
  verifier — the two places where a subtle bug would be most expensive.
* **Nothing was run against production.** No live endpoint, no real
  `/health`, no TLS or notification check.
