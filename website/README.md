# website/

The static site at snapworth.eu. The Vercel project's Root Directory is
`website`, and everything in this directory is published as it is, this file
and `seo/` included, so nothing private belongs here.

`worth/`, `guess.html`, `sitemap.xml` and `robots.txt` are generated by
`seo/build_seo.py` and `seo/build_guess.py`, and committed. `index.html`,
`invite.html`, `support.html` and `404.html` are written by hand.
`.github/workflows/website.yml` checks both kinds on every change.

## App Store campaign links

Every App Store link on the site is an App Store Connect campaign link (#204):

```
https://apps.apple.com/app/apple-store/id6788521307?pt=<PT>&ct=<ct>&mt=8
```

ASC → App Analytics → Campaigns lists impressions, downloads and proceeds for
each `ct`. A bare product link is credited to the referring domain and nothing
finer, so before this the homepage, the /worth guides, /guess and the invite
page were one number.

- `pt`, the provider token, is one constant: `PT` in `seo/campaigns.py`. It
  is the same in every campaign link the account generates. It is not a
  secret (it is in every link a visitor clicks), but nothing in the repo
  holds it, so the owner posts it.
- `ct` is chosen by us, one per surface, from the table below.
- The link names no storefront (`/us/`) and no slug, so the App Store opens
  each visitor's own storefront.

Counts in ASC are floors (only users who share analytics with developers), so
compare ratios between campaigns rather than totals.

A new /worth guide needs its `worth_<slug>` row here; the check names the
missing one. `worth_<slug>` is built in `build_seo.py`, `guess_web` in
`build_guess.py`. The hand-written links carry their `ct` in a `data-ct`
attribute, which is where `seo/apply_campaigns.py` reads it from.

**Off the site.** Not links on these pages, so the check does not read them,
but they are campaigns the dashboard will see. The owner generates them in
ASC's campaign generator with the same provider token:

| ct | Where it appears |
|---|---|
| `ig_bio` | Instagram profile link |
| `tiktok_bio` | TikTok profile link |
| `x_bio` | X profile link |

The share-card QR codes get their own values in #221 (1.5.2).

Excluded from all of this: the offer-code redeem URL `backend/referral.py`
builds (`apps.apple.com/redeem?...`), which opens Apple's redeem sheet and
cannot carry a campaign, and the Smart App Banner (`apple-itunes-app`), which
has no campaign field.

`PT` is `None` until the owner posts it on #204. Until then `app_store()`
refuses to build a link, so `build_seo.py` and `build_guess.py` exit with a
message naming #204, and `check_store_links.py` fails on every link.

### Finishing it: one constant, one command

1. In App Store Connect → App Analytics → Campaigns, generate any campaign
   link. The provider token is the value after `pt=`.
2. Set `PT = "<that value>"` in `website/seo/campaigns.py`.
3. From the repository root, on a clean tree:

   ```sh
   python3 website/seo/apply_campaigns.py
   ```

   It rewrites the eight links in `index.html` and the one in `invite.html`
   from their `data-ct`, regenerates `/guess`, then the /worth guides, the hub
   and the sitemap, and runs `check_store_links.py`. It commits nothing.
4. Review `git diff`, commit the same day (the sitemap stamps changed pages
   with today's date, and CI regenerates it from the commit's date), push.

Running `build_seo.py` and then `build_guess.py` again afterwards produces no
diff; website.yml checks exactly that.
