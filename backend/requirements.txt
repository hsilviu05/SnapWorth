# 0.133.0 is the first FastAPI release that drops the starlette upper bound
# (0.115.5 pinned starlette<0.42.0; 0.132.1 still capped at <1.0.0), so it is the
# minimum version that can take a patched starlette. Deliberately not the latest
# (0.141.1, which also works): 0.133.0 stops short of 0.137.0, which upstream
# flags as a major breaking release, and buys nothing extra security-wise.
fastapi==0.133.0
# Pinned explicitly rather than left transitive. It was only ever pulled in via
# FastAPI, which is precisely why seven advisories against it went unnoticed —
# an indirect dependency has no line in this file to review. 1.3.1 closes all
# seven, of which two were reachable: PYSEC-2026-1941 (multipart >1MB spool
# rollover blocking the event loop on /scan) and PYSEC-2026-249
# (max_fields/max_part_size silently ignored for urlencoded bodies).
starlette==1.3.1
uvicorn[standard]==0.52.1
google-generativeai==0.8.3
# Multipart parsing for the /scan upload. 0.0.31 closes seven advisories, all
# reachable by an unauthenticated POST: preamble and part-header parsing DoS
# (PYSEC-2026-3036/3037/3038/3039) and an unvalidated negative Content-Length
# (PYSEC-2026-3040). This is the highest-exploitability item in the tree — the
# upload path is the app's front door.
python-multipart==0.0.31
# NOT on the original fix list — surfaced by the audit added in this change.
# PYSEC-2026-2270: set_key()/unset_key() follow symlinks when rewriting .env,
# letting a local attacker overwrite arbitrary files. Not reachable here: the
# only use is load_dotenv() at main.py:55, and neither writer is ever called.
# Bumped anyway because clearing it outright is cheaper than carrying an audit
# allowlist entry that someone has to re-verify on every future review.
python-dotenv==1.2.2
pydantic==2.10.3
# Header-only image inspection for upload validation (decompression-bomb guard).
# Image.open() runs on attacker-supplied bytes, so the 17 advisories fixed by
# 12.3.0 — several heap out-of-bounds writes and memory corruption on malformed
# input — are on a reachable path. The magic-byte allowlist in imagevalidation.py
# already rejects the PSD/PDF/FITS/BDF/PCF vectors before Pillow sees them, which
# is why this ranks below multipart and cbor2 rather than above them.
Pillow==12.3.0
# Distributed rate limiting. Optional at runtime: without REDIS_URL the limiter
# degrades to per-process counters (see ratelimit.py).
redis==5.2.1
# App Attest attestation objects are CBOR-encoded. This parses attacker-supplied
# bytes on /auth/attest, which is unauthenticated by design (it is the bootstrap
# that mints the first token), so decoder bugs are directly reachable. 5.9.0
# closes an integer overflow in the C decoder (PYSEC-2025-238) plus PYSEC-2025-90
# and PYSEC-2026-2123.
cbor2==5.9.0
# StoreKit 2 signed transactions are ES256 JWS. 2.13.0 closes six advisories,
# including PYSEC-2026-176, a verifier-side algorithm allow-list bypass that
# would in principle be an entitlement-forgery path to free Pro. That one is
# already defeated independently by the explicit `alg != "ES256"` rejection in
# entitlements.py:211, which runs before jwt.decode — the upgrade removes the
# reliance on that single check rather than introducing the protection.
#
# 2.13.0 also clears PYSEC-2025-183 (CVE-2025-45768, "weak encryption"), which
# has no listed fix version. That advisory was disputed on the grounds that key
# length is the caller's choice; 2.13.0 answers it by emitting
# InsecureKeyLengthWarning for HMAC keys under 32 bytes. It never applied here
# in any case — both call sites are ES256 over an EC P-256 key
# (entitlements.py:219 verifies, devicecheck.py:72 signs) and no HMAC key
# exists in production code. No audit allowlist entry is therefore needed.
PyJWT==2.13.0
# Backs the X.509 chain walk that validates StoreKit transactions against the
# pinned Apple Root CA G3 (entitlements.py:_verify_chain) and the App Attest
# chain (appattest.py), so its correctness is load-bearing for entitlement
# integrity. Earlier bumps here cleared PYSEC-2026-35, PYSEC-2026-1284,
# PYSEC-2026-2141 and GHSA-537c-gmf6-5ccf.
#
# 50.0.0 closes three CVEs published against 48.0.1 *after* it was pinned — new
# disclosures, not a regression, which is exactly the drift the pip-audit gate
# exists to catch:
#
#   PYSEC-2026-3552  CVE-2026-69247  pkcs7_decrypt_* leaked the RSA-recovered
#                    length by distinguishable outcome and by timing — a
#                    Bleichenbacher oracle for anything decrypting attacker-
#                    supplied EnvelopedData. Needs 50.0.0. NOT REACHABLE here:
#                    PKCS7 is not used anywhere in this codebase.
#   PYSEC-2026-3553  CVE-2026-69249  Chains containing duplicate self-signed
#                    certificates blow up exponentially during resolution;
#                    >5s to reject a crafted chain. Needs 49.0.0.
#   PYSEC-2026-3554  CVE-2026-69248  A leaf wildcard SAN of *.example.com is
#                    wrongly accepted under an intermediate constrained to
#                    foo.example.com, escaping the permitted name tree.
#                    Needs 49.0.0.
#
# 3553 and 3554 both live in the x509.verification API (PolicyBuilder / Store /
# Verifier), which this codebase does not use — the chain walk in
# entitlements.py and appattest.py is manual, comparing a pinned root by DER
# bytes and verifying each link with key.verify(). So none of the three is
# directly exploitable here; the upgrade is taken because the primitives
# underneath are load-bearing and 50.0.0 is the single version clearing all
# three.
cryptography==50.0.0
# DeviceCheck API calls.
httpx==0.28.1
